01 — Overview

The problem with fantasy projections

Every week, millions of fantasy football players make lineup decisions based on one question: who is going to score? Tools like ESPN, Yahoo, and FantasyPros give you projections, but the numbers are a black box. You have no idea how they were generated, what data they use, or whether they actually hold up.

This project started from a simple idea: build the whole thing myself. Not a frontend that pulls from someone else's API, but the real deal. Historical data ingestion, feature engineering, a machine learning model trained from scratch, and then a dashboard to make it all usable by a real person.

The dashboard is not the star of this project, the ML backend is. But without a frontend, the system is invisible. The design job was building something fast, legible, and credible enough to surface the model's output to an actual user.

The backend ingested 41,892 rows of NFL player stats from 2016 to 2023 using nfl-data-py. Features were engineered from that data including 3-game and 5-game rolling averages, opponent defensive rank, snap percentage trends, and home/away splits. Two XGBoost models were trained: one specifically for QBs and one for all other skill positions. Model artifacts were serialized to AWS S3, and inference results for the full 2023 season (5,294 rows) were stored in PostgreSQL on RDS, served through Lambda handlers behind API Gateway.

03 — Design Approach

Designing for a sports data context

Fantasy football apps have an established visual language. Dense data tables, dark backgrounds, bold numbers, color-coded positions. The most credible tools in the space like ESPN and the Sleeper app use dark UI so the chrome fades away and the data is what you actually see.

Going with a dark theme was not just a style preference. It was a deliberate choice to match the visual context a fantasy player already lives in. Someone opening this dashboard should feel immediately at home, not like they landed on a generic data table.

Design reference: Sleeper app. Near-black background with a cool blue-grey tint, slightly elevated card surfaces, barely-there borders, and vibrant colorful data on top. The goal was for the dark chrome to disappear so the projections pop.

Color was used functionally, not decoratively. Each position gets its own distinct color so a user scanning the table can identify position groupings without reading every label. Projected points are highlighted in green throughout, creating a consistent visual anchor for the single most important number on the page.

05 — Honest Critique

What worked, and what I would do differently

Stepping back from the V1 build, a few things landed well and a few things are clear areas for improvement. The most useful thing a case study can do is be honest about both.

What worked
✓
The data flow worked end to end

The API returned real, differentiated projections and the frontend displayed them correctly. The core loop worked: pick a position, see the right players ranked with real numbers.

✓
Position color coding made the table scannable

The colored position badges let users parse position groupings at a glance without reading every label in the POS column. It sounds small but it noticeably reduces the cognitive load of reading a dense table.

✓
Stat cards added real value above the fold

Surfacing the top player at each position above the table gave users a quick top-line read. In a real fantasy context, that summary card is often the only thing you need to confirm a start decision.

What I would do differently
!
No visible week context

There is no indicator on screen for which week the data is showing. Week selection is handled at the API level rather than in the UI, which means a user opening the dashboard has no immediate frame of reference. This is a real usability gap and the fix is straightforward: surface the current week prominently in the header.

!
Progress bars do not scale relatively

Every player's projected points bar renders at roughly the same width. They should scale against the highest projected score for that week so you can visually read the drop-off between players. Right now the bars add visual noise without adding information.

!
Player modal data is incomplete

The detail modal shows Games, Touchdowns, and Total Yards as 0. These fields exist in the UI but are not populated by the current API response. For Week 1 specifically the 0 game count is technically accurate since it is a projection with no games played yet, but the presentation is confusing without that context. The modal needs either real supporting stats or clearer labeling of what it is showing.

!
Stat cards missing TE

The top row shows QB, RB, and WR but no tight end. TE is one of the most contested roster decisions in fantasy given how thin the position is, and its absence from the summary cards is a noticeable gap.

Player modal — core projection and rank display correctly, but secondary stats are unpopulated
06 — Reflection

What this project actually taught me

The biggest thing I took away from this is that building the backend and building the frontend require completely different mental models, and that designing a UI for a system you built yourself gives you a real edge. I knew exactly what the API could and could not return, what the model's accuracy limits were, and where the data was likely to look wrong.

A good example is the Week 1 cold start problem. The rolling features the model relies on (3-game and 5-game averages) had no prior-week data to draw from for Week 1, which caused near-identical projections for every player. Because I understood the full pipeline, I could immediately tell it was a feature engineering issue and not a UI bug. The fix involved a cross-season lookback using end-of-2022 data, retraining the model, and regenerating predictions. R² improved from 0.340 to 0.347 after the fix.

The critique in the previous section is genuine. The progress bars are broken in a way I shipped anyway, and the modal feels incomplete. That is real. Being able to look at your own work clearly and name what is wrong is part of the job, and this project gave me a lot of practice doing that.
